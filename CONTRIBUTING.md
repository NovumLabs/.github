# Contributing to Novum Labs

Thank you for your interest in contributing to **Novum Labs**.

We welcome researchers, software engineers, students, educators, and open-source contributors who want to advance artificial intelligence research and build useful, reliable software.

Our goal is to foster a collaborative environment where ideas are tested rigorously, code is maintained carefully, and technical claims are supported by evidence.

## 1. Ways to Contribute

You can contribute to Novum Labs projects in several ways:

- **AI Research:** Develop hypotheses, reproduce experiments, evaluate models, and improve research methodologies.
- **Software Development:** Implement features, fix bugs, improve performance, and refactor existing code.
- **Documentation:** Improve README files, API documentation, tutorials, examples, and technical explanations.
- **Testing and Evaluation:** Add unit tests, identify edge cases, evaluate model outputs, and report reproducible failures.
- **Datasets and Benchmarks:** Improve data-processing pipelines, evaluation datasets, and benchmark methodology, subject to licensing and privacy requirements.
- **Community Support:** Help answer technical questions, review contributions, and suggest improvements.

## 2. Before You Start

Before contributing:

1. Read the README of the repository you want to contribute to.
2. Check existing issues and pull requests to avoid duplicating work.
3. Review the project's license and contribution requirements.
4. For significant changes, open an issue to discuss your proposed approach.
5. Confirm that you have permission to use any datasets, models, libraries, or other third-party resources involved.

Individual repositories may define additional requirements. When they do, follow the repository-specific instructions.

## 3. Reporting Bugs

When reporting a bug, provide enough information for another developer to reproduce it.

Include:

- A clear and descriptive title.
- The expected behavior.
- The actual behavior.
- Steps to reproduce the problem.
- Your operating system, relevant software versions, and environment details.
- Relevant error messages or logs, with secrets and personal information removed.
- A minimal code example or test case when possible.

Please search existing issues before submitting a new report.

Do not publish API keys, passwords, access tokens, private datasets, or confidential client information in public issues.

## 4. Suggesting Features

Feature requests should explain:

- The problem you want to solve.
- Why the proposed feature would be useful.
- The intended behavior and expected outcome.
- Possible implementation approaches, if known.
- Relevant use cases, examples, or supporting evidence.

For major architectural changes, discuss the proposal with project maintainers before investing significant implementation effort.

## 5. Development Workflow

For repositories that use Git, the recommended workflow is:

1. Fork the repository if you do not have direct write access.
2. Clone your fork to your local machine.
3. Create a separate branch for your changes.
4. Make focused, understandable changes.
5. Add or update tests where appropriate.
6. Run the relevant tests and checks locally.
7. Commit your changes with a descriptive commit message.
8. Open a pull request explaining what changed and why.

Example branch names:

- `feature/add-model-evaluation`
- `fix/tokenizer-validation`
- `docs/improve-installation-guide`
- `test/add-api-unit-tests`

Avoid combining unrelated changes in one pull request.

## 6. Code Quality Standards

We aim to maintain software that is understandable, reliable, and maintainable.

Contributors should:

- Follow the conventions and formatting tools already used by the repository.
- Write clear, descriptive names for functions, variables, classes, and modules.
- Keep functions focused and avoid unnecessary complexity.
- Add comments when they clarify non-obvious decisions.
- Handle errors explicitly and validate untrusted inputs.
- Add appropriate tests for new functionality and bug fixes.
- Update documentation when behavior, configuration, or APIs change.
- Avoid committing generated files, local environment files, credentials, or unrelated changes.

Do not introduce unnecessary dependencies or breaking changes without explaining their justification.

## 7. AI Research and Machine Learning Contributions

Research contributions should prioritize reproducibility, methodological clarity, and honest reporting.

Where applicable, document:

- The research question and hypothesis.
- Dataset sources, licenses, preprocessing, and limitations.
- Model architecture and relevant implementation details.
- Training configurations, hyperparameters, and random seeds.
- Software, library, and hardware requirements.
- Baselines and evaluation metrics.
- Experimental results, including negative or inconclusive results.
- Known limitations, failure cases, and potential sources of bias.

Distinguish clearly between measured results, hypotheses, estimates, and future plans.

Do not claim that a model outperforms existing methods unless the comparison is supported by an appropriate and reproducible evaluation.

Never include private, sensitive, or improperly licensed training data.

## 8. Responsible AI and Security

Contributors are expected to consider the safety, privacy, reliability, and potential misuse of the systems they develop.

Please:

- Follow applicable data protection and licensing requirements.
- Avoid exposing personal information or confidential material.
- Document relevant model limitations and foreseeable failure modes.
- Use secure configuration and environment variables for secrets.
- Avoid introducing malicious code, hidden data collection, or unauthorized access.
- Report suspected security vulnerabilities through the project's designated private reporting channel rather than a public issue.

See the relevant repository's `SECURITY.md` for its reporting instructions, when available.

## 9. Commit Messages

Use concise commit messages that describe the change.

Examples:

- `Add model evaluation tests`
- `Fix API input validation`
- `Improve dataset documentation`
- `Update installation instructions`
- `Add reproducibility configuration`

Keep each commit focused on a logical unit of work.

## 10. Pull Request Guidelines

Every pull request should include:

- A clear summary of the changes.
- The motivation or problem being addressed.
- Relevant issue references, if applicable.
- Tests performed and their results.
- Documentation updates, where necessary.
- Known limitations or follow-up work.

Before submitting:

- Verify that the relevant tests pass.
- Review your changes for accidental files or sensitive information.
- Resolve merge conflicts where possible.
- Ensure that your contribution complies with the project's license and requirements.

Maintainers may request revisions, additional tests, or clarification before merging.

Submitting a pull request does not guarantee acceptance. Contributions are reviewed according to project goals, technical quality, maintainability, security, and research integrity.

## 11. Community Standards

All contributors are expected to communicate respectfully and constructively.

We encourage thoughtful disagreement, evidence-based technical discussion, transparent feedback, and collaboration across experience levels.

Harassment, discrimination, personal attacks, deliberate disruption, and other unacceptable conduct are not tolerated.

Please follow the applicable `CODE_OF_CONDUCT.md` and any project-specific community rules.

## 12. Licensing and Attribution

By contributing, you confirm that:

- You have the right to submit the contributed material.
- Your contribution does not knowingly infringe third-party rights.
- Third-party code, data, models, and research are properly attributed where required.
- You understand the contribution terms and license applicable to the target repository.

Unless a project specifies otherwise, contributions are subject to that repository's existing license and contribution requirements.

Do not assume that all Novum Labs repositories use the same license.

## 13. Recognition and Collaboration

We value contributions of all sizes, including bug reports, documentation improvements, testing, research feedback, and substantial code changes.

We aim to recognize meaningful contributions transparently and build long-term collaborations around useful software and credible research.

## 14. Questions

For project-specific questions, use the repository's documented support channel or open a discussion where available.

For bugs and feature requests, use the project's issue tracker.

For security concerns, follow the designated private reporting instructions.

Thank you for helping Novum Labs build better AI systems, stronger research practices, and useful open-source software.
